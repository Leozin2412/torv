## Revisão de código

**`auth.middleware.js` (JWKS) — sem achados.** Bate exatamente com o plano: `createRemoteJWKSet` + `jwtVerify` contra `${SUPABASE_URL}/auth/v1/.well-known/jwks.json`, `issuer` validado, `request.user.userId = payload.sub` normalizado logo após verificação. Token ausente → 401 (`Access token is missing`), inválido/expirado → 403 (`Invalid or expired token`) — mesmos códigos do middleware antigo, confirmando o requisito do "Riscos" da spec (linha 61). Os 8 call sites em `diet.controller.js`/`profile.controller.js` que fazem `const { userId } = request.user` continuam intocados e funcionando (confirmado ao vivo abaixo). Nota informativa, não bloqueante: não valida `aud` (audience) do token — só `issuer` + assinatura. Não é uma falha de segurança (só o projeto Supabase consegue assinar um JWT com esse `issuer`), mas seria defesa em profundidade adicional se algum dia for necessário.

**Trigger `handle_new_user` (SQL) — sem achados.** Migration `20260918165833_supabase_auth_link` bate com o plano: `SECURITY DEFINER` + `SET search_path = public` (mitiga o ataque clássico de search_path hijacking em função `SECURITY DEFINER` — boa prática presente desde o plano). As 4 inserções (`users`, `user_profiles`, `user_measurements`, `user_streaks`) rodam na mesma transação do `INSERT` em `auth.users` — atômico por natureza de trigger, sem necessidade de `BEGIN/COMMIT` manual. `username` derivado de `raw_user_meta_data` com fallback determinístico (`email_local_part + '_' + primeiros 8 chars do id`) se ausente ou vazio. Bônus não pedido no plano, adicionado pelo Torv Database: `DROP FUNCTION IF EXISTS fn_register_new_user(...)` — remove uma função morta que referenciava a coluna `password_hash` recém-removida, evitando deixar lixo quebrado no schema. Confirmado ao vivo: as 4 linhas foram criadas corretamente para uma conta nova (ver usabilidade, passo 1).

**Achado MEDIUM (não bloqueante) — bounds de peso/altura perderam mensagem específica.** As constraints `CHECK` de `weight_kg`/`height_cm` (20-300kg, 50-250cm) migraram para o banco (migration, linhas 21-23), como o plano pedia, substituindo a validação que existia em `authController.register`. Mas o wizard de cadastro (`Register/index.tsx:85`) só valida presença (`!weight || !height`), não os limites — um valor fora da faixa passa pela validação do app, chega no `supabase.auth.signUp()`, o trigger falha no `INSERT` (constraint violation), o signup inteiro é revertido, e o app mostra só a mensagem genérica "Falha ao criar conta. Tente novamente." (o catch só trata a mensagem `already registered` especificamente). Antes, o app-layer dava um erro específico de "peso/altura fora da faixa". Não é uma regressão de segurança nem permite dado inválido passar (o banco ainda barra), só piora a mensagem de erro pra esse caso extremo — não testado ao vivo por não fazer parte do roteiro pedido, mas verificado por leitura de código.

**Achado LOW (cosmético) — dependências mortas no backend.** `bcrypt` e `jsonwebtoken` continuam em `BackEndTorv/package.json` sem nenhum importador (`grep` confirmou zero referências em `src/`). O plano só pedia remover `auth.controller.js`/`auth.routes.js`/`auth.repository.js` e o arquivo `jwt-secret.js` (feito), mas não instruía `npm uninstall` dessas duas libs — ficaram como peso morto. Contraste: no frontend, `@react-native-async-storage/async-storage` foi corretamente desinstalado (Task 6 Step 4). Não afeta funcionamento, só limpeza pendente.

**Commit extra `961e4fa` (não estava no plano, auto-correção do Frontend) — verificado, correto.** `expo-secure-store` não tem build web (stub `export default {}`) — chamar `getItemAsync`/`setItemAsync` no navegador lançaria exceção, quebrando o storage de sessão inteiro no alvo web (exatamente a mesma classe de bug do achado CRITICAL do round 1 da feature `retroactive-date-filter`, um módulo nativo-só usado sem guarda de plataforma). A correção usa `Platform.OS === 'web' ? undefined : ExpoSecureStoreAdapter` — deixar `storage: undefined` no web reaproveita o fallback `localStorage` que o próprio `@supabase/supabase-js`/`auth-js` já tem embutido (`GoTrueClient.js`), em vez de escrever um adapter novo. Testado ao vivo abaixo (persistência de sessão após reload). Risco anotado na spec (linha 59, limite de ~2KB do item no Keychain iOS) permanece não testável neste portal — é nativo-only, fora do alcance do Expo web.

**Resto do diff (Login/Register/AuthContext/api.ts/schema.prisma/server.js) bate exatamente com o plano, sem desvios.** `toIsoDate` do Register confere certo com o formato que a trigger espera (`YYYY-MM-DD` via `::date`) — confirmado ao vivo (ver usabilidade, `birth_date` retornado certo pela API).
